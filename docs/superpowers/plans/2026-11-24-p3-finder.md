# P3 Emergency Finder, Matching Engine, First Aid, Directory — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Public (no login) Finder: pick an emergency (+ blood group, location) → hospitals ranked by how well they can treat it now, with bn/en reasons; first-aid card with Call 999 and source; directory-only hospitals in an "Unverified — call before going" section.

**Architecture:** Pure, unit-tested `rankHospitals` in `src/server/matching/` fed by a single DB snapshot query in `src/server/finder/`. Finder is server-rendered from URL search params (shareable, near-zero client JS); only the location button and filter auto-submit are client components.

**Tech Stack:** as P1. **Spec:** `CLAUDE.md` §1 (module 2), §3.3, §3.4, §4, §5, §6 + `docs/PLAN.md` P3 + P1 plan interfaces (`docs/superpowers/plans/2026-11-24-p1-data-auth.md`).

## Global Constraints
- All P1 Global Constraints apply.
- Finder and first aid are public; never require login. "DEMO DATA — not real hospital availability" banner stays (root layout).
- Performance: Finder route initial JS < 150 KB gzipped; Server Components by default; no new runtime dependencies; skeleton (`loading.tsx` / Suspense fallback), never blank. Touch targets ≥ 44px; works 360–1920px; no horizontal scroll.
- Matching is a pure function (no Prisma imports in `src/server/matching/`), test-first.
- Stale = resource `updatedAt` older than 30 minutes (constant `STALE_AFTER_MS = 30 * 60_000`).
- Reasons are bilingual `{ bn, en }` with prefix ✅ / ⚠️ / ❌.
- First-aid card always shows: do's, don'ts, Call 999 (`tel:999`), source name linked to source URL, disclaimer "This is first aid, not a substitute for medical treatment." (bn + en). No invented medical text — content comes only from the `FirstAidGuide` table.
- i18n strings in `src/lib/i18n/finder.ts` only. Lang from `lang` cookie via `parseLang`.

## Review Focus
- No/invalid location (`lat=999`, missing) → results still ranked by score; distance shown as "—"; radius filter ignored with a notice.
- Blood group not given for a blood-requiring condition → only O_NEG counts, reason says so.
- All hospitals filtered out → empty state suggests widening radius / removing filters, plus directory section and Call 999 still visible.
- Condition code not in DB (`?condition=FOO`) → condition picker shown with a validation notice, not a 500.
- Hospital with a CRITICAL requirement missing appears below all suitable ones, labelled "Not suitable", with ❌ reason.

### Task 1: Matching engine (pure, test-first)

**Files:** Create `src/server/matching/types.ts`, `src/server/matching/geo.ts`, `src/server/matching/rank.ts`, `src/server/matching/index.ts`; Test `tests/unit/geo.test.ts`, `tests/unit/rank.test.ts`

**Produces:**
- `haversineKm(a: {lat:number;lng:number}, b: {lat:number;lng:number}): number`; `isValidCoord(p: {lat:number;lng:number}): boolean`.
- Types: `MatchRequirement = { resourceCode: string | null; isBlood: boolean; level: "CRITICAL"|"PREFERRED"; minQuantity: number; nameBn: string; nameEn: string }`; `MatchResource = { code: string; kind: "COUNTABLE"|"STATUS"; available: number; total: number; isAvailable: boolean; updatedAt: Date; bloodGroup: BloodGroup | null; nameBn: string; nameEn: string }`; `MatchHospital = { id: string; lat: number; lng: number; resources: MatchResource[] }`; `MatchInput = { requirements: MatchRequirement[]; bloodGroup: BloodGroup | null; origin: {lat:number;lng:number} | null; now: Date; hospitals: MatchHospital[]; compatibleDonors: Record<BloodGroup, BloodGroup[]> /* recipient → donors */ }`; `Reason = { kind: "ok"|"warn"|"missing"; bn: string; en: string }`; `RankedHospital = { hospitalId: string; score: number; rank: number; suitable: boolean; distanceKm: number | null; stale: boolean; reasons: Reason[]; lastUpdatedAt: Date | null }`.
- `rankHospitals(input: MatchInput): RankedHospital[]` — sorted: suitable first, then score desc, then distance asc; `rank` 1-based over the sorted list.

Scoring algorithm (decided here):
```
requirement satisfied:
  STATUS resource  → isAvailable
  COUNTABLE        → available >= minQuantity
  isBlood          → sum(available of BLOOD_* rows whose bloodGroup ∈ compatibleDonors[recipient]) >= minQuantity,
                     recipient = bloodGroup ?? (treat as unknown: donors = [O_NEG]) + warn reason "Blood group unknown — counting O− only"
weights: CRITICAL 3, PREFERRED 1
capability = 70 × (satisfied weight / total weight)           (no requirements → 70)
distance   = origin ? 20 × max(0, 1 − d/30)  : 10              (d km, Haversine)
freshness  = 10 if none of the requirement-matched rows is stale, else 0; stale ⇒ warn reason "Data not updated for N min"
score = round(capability + distance + freshness), clamped 0..100
suitable = every CRITICAL satisfied; any CRITICAL missing ⇒ ❌ reason, suitable=false
reasons order: ❌ missing critical, ⚠️ missing preferred / stale / unknown blood, ✅ satisfied (with "N available" for countables)
```

- [ ] **Step 1: Failing tests:**
  - geo: Dhaka (23.8103, 90.4125) → Chattogram (22.3569, 91.7832) ≈ 213 km ±3; same point 0; `isValidCoord({lat:91,lng:0})` false.
  - rank: all criticals satisfied → suitable, ✅ reasons; one critical missing → not suitable and ranked after a lower-scoring suitable hospital; preferred missing lowers score vs identical hospital with it; stale rows → `stale: true`, freshness 0, ⚠️ reason containing minutes; nearer hospital outranks farther identical one; origin null → distanceKm null and both get 10; blood: recipient A_NEG with only O_NEG stock → satisfied, with only A_POS stock → missing; bloodGroup null with O_POS stock only → missing + unknown-blood warn; `minQuantity` 2 with available 1 → missing; scores within 0..100; ranks 1..n contiguous; every reason has non-empty bn and en.
